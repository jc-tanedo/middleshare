# Repository audit — 2026-10-23

Review baseline: `c2a1244` (the `v0.6.0` release), plus the changes accompanying this report. This is a source/history review and local build verification, not a penetration test or a complete dependency vulnerability assessment.

## Summary

No MiddleShare signing keys, passwords, access tokens, or other project credentials were detected in the nine reachable commits or the tracked/new working files examined. There were no credential-like keystore/private-key filenames in the reachable object inventory. Secret detection is heuristic; these results do not establish that every possible credential has been found.

One application security issue was fixed: a caller could forge an intent extra to skip video-download confirmation. CI credentials and action dependencies were hardened, source formatting was standardized, and the README was reorganized.

## Security findings

| Finding | Assessment | Resolution |
| --- | --- | --- |
| Caller-controlled download confirmation | **Medium.** The exported `ShareActivity` accepted `dev.middleshare.CONFIRMED=true` from any caller. A foreground app could launch it with that extra and trigger a download without the quality confirmation step. No arbitrary command execution was established. | Removed the boolean trust decision. Only `VideoDownloadActivity`, declared `exported=false`, starts a confirmed download. Added regression tests for a forged extra and the private manifest entry. Version 0.6.1 requires an updated add-on. |
| Mutable GitHub Action references | **Hardening.** `@v3`/`@v4` references could change independently of this repository. | Pinned each action to its upstream commit, retained version comments, and added weekly Dependabot updates for Actions. |
| Checkout retained the workflow token | **Hardening.** Git checkout persisted authentication into local Git configuration during build steps. | Set `persist-credentials: false` in both workflows. Publication still uses the explicitly scoped GitHub token in its own step. |
| Incomplete local-secret ignore rules | **Low.** Keystores were ignored, but `.env`, PKCS#12 files, and some common signing-property files were not. | Added ignore rules for those local credential formats. Ignore rules do not replace secret scanning. |
| Upstream embedded credential patterns | **Informational; provenance verified.** Unpacking yt-dlp exposes token/key constants that a generic scanner flags. These are already present in upstream source, not credentials introduced by MiddleShare. | Retained the unmodified verified bundle and documented the findings below. No live credential validation was attempted. |

### Credential scan evidence

Gitleaks **8.24.3** was downloaded from its official release, checked against the upstream SHA-256 checksum manifest, and run with fully redacted reports:

- `gitleaks git --log-opts='--all --full-history' --redact=100`: nine reachable commits, no findings.
- `gitleaks dir` on a snapshot of tracked/new project files, with decoding depth 2: no findings.
- A separate scan of unpacked historical zip/jar payloads: two unique archives, 1,086 members, 92 findings, all in yt-dlp extractor Python files. Rule counts: 66 generic API-key patterns, 20 JWT patterns, five Google API-key patterns, and one AWS access-key pattern.

The bundled yt-dlp zipapp's SHA-256 matches the official **2026.10.21** `SHA2-256SUMS` release manifest:

```
b7af77f686e95f7845ce8d09d21957718febb8b48b30555adb9dd2292ad7bf14
```

That match establishes the upstream provenance of the embedded values. It does not establish that those values are inactive, harmless, or owned by this project. Their validity and upstream service authorization were not tested. No findings were hidden with a repository-wide allowlist, and no token values are reproduced here.

The historical object inventory was also checked for `.env`, keystore, PKCS#12, PEM/private-key, and signing-property filenames; none were found. This is complementary filename evidence, not a substitute for content scanning.

### Existing controls reviewed

- Only the video flavor requests internet access; no video native libraries or yt-dlp are included in the core APK.
- The provider is non-exported, grants read access to individual UUID-named cache files, rejects write modes, and validates canonical paths.
- Incoming image shares require `content://` URIs and are bounded by file/pixel limits. Link parsing requires HTTP(S), rejects URL user information, and accepts one link at a time.
- Add-on handoff verifies package identity, minimum version, enabled state, and signing-certificate equality.
- Custom format IDs have a strict allowlist; arbitrary yt-dlp argument expressions are not accepted. Requests keep TLS verification enabled and do not request re-encoding.
- Release signing values are referenced through GitHub secrets rather than literals. The workflow removes its temporary signing key and verifies release APK certificates. Pull-request builds receive no signing secrets; there is no `pull_request_target` workflow.
- The Gradle distribution checksum, pinned runtime artifacts, bundled extractor checksum, and third-party attribution guard remain in place.

## Code quality and structure

The current single-module structure is appropriate for a small native app. Shared, core-only, video-only, and flavor-specific test source sets are explicit. A broad package/module migration would add churn without resolving a present boundary problem.

Changes made:

- Extracted the site-preference dialog controller into `SitePreferences`, leaving `MainActivity` responsible for the home screen.
- Standardized handwritten Java with Google Java Format **1.24.0**, AOSP mode, and added `.editorconfig` conventions.
- Renamed the obsolete `Ui.GREEN` color role to `Ui.ACCENT`, which works for both the green light palette and Nord dark palette.
- Removed an immediately overwritten quality-default read from the add-on screen.
- Updated add-on fixtures to use the current compatibility boundary instead of hard-coded accepted version numbers.
- Kept generated catalogs, native payloads, and upstream license texts intact.

Remaining maintenance opportunities: several English UI strings still live in Java rather than string resources, so localization is incomplete. The attribution generator is compact and could benefit from a separate readability refactor. Neither requires a broad rewrite before making the repository public.

## Validation and limits

- **85 unit tests passed:** 36 core and 49 video, including the two new security regression tests.
- Lint passed for both debug flavors without issues.
- Core/video debug and optimized release builds completed. Local release APKs were unsigned; this audit did not access production signing secrets or publish a release.
- Actionlint **1.7.7** passed for both workflows.
- Java formatting, local documentation links, and whitespace were checked.

The review did not inspect GitHub-hosted secret values, prior workflow logs/artifacts, release assets, organization rules, or branch/tag protection settings. It did not inspect conversations or personal credential stores, probe live video services, audit every native/transitive dependency for CVEs, or establish native subprocess behavior on a phone. Git authorship metadata includes maintainer attribution and becomes visible with the repository history.

Before changing visibility, review prior Actions logs/artifacts and release attachments in GitHub, and enable private vulnerability reporting and available secret-scanning/push-protection features. Published v0.6.0 binaries still have the confirmation issue; the fix is in the 0.6.1 source and needs a new release to reach installed apps.
